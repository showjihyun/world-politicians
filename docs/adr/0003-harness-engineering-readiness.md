# ADR 0003 — 하네스 엔지니어링을 위해 아직 없는 것

- 상태: 진단 (구축 전)
- 날짜: 2026-08-29

## 왜 지금 이 문서인가

이 저장소의 작업은 지금까지 전부 단일 작업자가 즉흥적으로 처리했다. 같은 종류의
일이 반복되는데도 매번 처음부터 다시 판단했고, 그 과정에서 반복적으로 같은 유형의
사고가 났다. 하네스(전문 에이전트 + 스킬)를 붙일 만한 지점이 분명히 있다.

다만 **하네스를 지금 바로 구축하면 안 되는 이유**가 있어서, 무엇이 먼저인지를
먼저 기록한다. 하네스는 에이전트가 스스로 검증할 수단이 있을 때만 작동한다.
그 수단이 없으면 에이전트가 자기 결과를 확인 없이 보고하고, 그건 지금보다 나쁘다.

## 현황 감사

```
.claude/agents/    없음
.claude/skills/    없음
.claude/commands/  없음
CLAUDE.md          없음
```

즉 신규 구축 대상이다.

### 하네스가 이미 기댈 수 있는 것

에이전트가 스스로 "됐다/안 됐다"를 판정할 수단은 이번에 갖춰졌다.

| 수단 | 실행 | 소요 |
| --- | --- | --- |
| 단위 테스트 (도메인) | `npm test` | 약 0.4초 |
| E2E (실브라우저) | `npm run e2e` | 약 90초 |
| 타입 검사 | `npx tsc --noEmit` | 수초 |
| 빌드 | `npm run build` | 약 6초 |
| CI | push·PR 마다 위 셋 | — |

순수 도메인 층(ADR 0001)이 분리돼 있어 에이전트에게 좁고 검증 가능한 과제를
줄 수 있다. 파이프라인 스크립트는 대부분 `--dry` 를 지원해 파괴적 변경 전에
미리보기가 가능하다.

### 하네스가 붙을 반복 작업 (이번 세션에서 실제로 반복된 것)

| 작업 | 반복 횟수 | 현재 상태 |
| --- | --- | --- |
| 근거 수집·필터·재수집·검증 | 6회 (collect → filter → recollect → gdelt → rebuild → normalize) | 스크립트 6개, 조율 문서 없음 |
| 데이터 감사 (링크 생존·날짜·라벨·화이트리스트) | 4회 | 매번 임시 스크립트 작성 후 삭제 |
| Reddit 공유 글 작성 | 3회 (서브레딧별 프레이밍 상이) | 스크래치패드에만 존재 |
| 야간 파이프라인 사고 대응 | 3회 (누적 소실·git add 경로·수집시각) | 사후 대응 |

## 하네스 구축 전에 반드시 필요한 것

### 1. 데이터 감사를 실행 가능한 명령으로 — **완료 (2026-08-29)**

이번에 네 번 돌린 감사가 전부 임시 스크립트였고 매번 지워졌다. 확인한 항목:

- 화이트리스트 밖 매체 유입 (실제로 9건 발견)
- 링크 생존 — 404/410 (실제로 5건 발견)
- 날짜 정합성 — 미래 날짜, 수집창 위반, 형식 오류
- 매체명·제목 표기 품질 (실제로 443건 발견)
- 근거 커버리지 (218/266 → 64/266 변화 추적)

**에이전트에게 "데이터 품질을 확인하라" 고 지시하려면 판정이 결정적이어야 한다.**
`npm run audit:data` 가 종료 코드로 답하지 않으면, 에이전트는 "확인했습니다" 라고
보고하고 실제로는 아무것도 확인하지 않는다. 이것이 하네스 이전에 와야 하는 첫 번째다.

**구현됨.** `scripts/audit/` — 판정 규칙(`checks.mts`)과 I/O(`data.mts`)를 분리했고,
규칙에는 단위 테스트 29개가 붙어 있다. 감사 자체가 틀리면 감사가 무의미하므로
규칙도 검증 대상이다.

검사 항목은 전부 실제로 데이터에 들어왔던 문제다: 허용 목록 밖 매체 · 미래/형식오류
날짜 · GDELT 하한 위반 · 수집 시각 역전 및 정체 · 매니페스트와 파티션 불일치 ·
인물 id 참조 무결성 · HTML 엔티티 잔존 · 제목 내 매체명 중복 · 확인 불가 리다이렉트
URL · 엣지 내 중복 · **문서 수치와 실제 데이터의 괴리**.

불량 데이터를 주입해 종료 코드 1 을 반환하는 것까지 확인했다. CI 와 야간 워크플로
양쪽에 걸었고, 야간 쪽은 **커밋 전에** 돌린다 — 커밋된 뒤에 알면 되돌려야 한다.
WARN 은 CI 를 막지 않는다. 경고로 빌드를 세우면 아무도 경고를 안 본다.

### 2. 도메인 경계의 기계적 강제

ADR 0001 이 "도메인은 `../data` 나 `node:fs` 를 import 하지 않는다" 고 규정하지만
**강제하는 것이 없다.** 사람은 리뷰로 잡을 수 있지만 에이전트는 규칙을 문서에서만
읽고 어긴다. import 제한 lint 규칙이 필요하다. 없으면 하네스를 돌릴수록 경계가
녹고, ADR 0001 이 무효화된다.

### 3. CLAUDE.md — 암묵 규칙의 기록

이번 세션에서 사고를 낸 규칙들은 전부 코드 어디에도 적혀 있지 않았다.

- 이 저장소 파일은 CRLF 다. `\n` 기준으로 치환하면 매칭이 조용히 실패한다
  (실제로 3회 발생)
- 파괴적 스크립트는 `--dry` 를 먼저 돌리고 제거율을 보고 반영한다
- LLM 배치는 판정을 못 받으면 원본을 유지한다 — 침묵을 삭제로 해석하면
  API 오류 한 번에 데이터가 날아간다 (dry-run 에서 503 2회 발생)
- `generatedAt` 은 재처리가 갱신하면 안 된다
- 워크플로가 커밋하는 경로는 출력 구조를 바꿀 때 함께 고쳐야 한다
  (실제로 야간 실행이 깨질 뻔했다)

에이전트는 새 세션마다 이걸 모른 채 시작한다. CLAUDE.md 가 없으면 같은 사고가
반복된다.

### 4. `--dry` 와 백업 관례의 통일

스크립트마다 다르다. `collect.mts` 는 `--fetch` 로 부작용을 켜고, `filter.mts` 와
`rebuild.mts` 는 `--dry` 로 끈다. 에이전트가 안전한 쪽을 기본으로 고르게 하려면
관례가 하나여야 한다.

## 구축한다면 — 팀 구성안

이번 세션의 실제 작업 분포에 근거한 초안이다. 지금 만들지 않는다.

| 에이전트 | 담당 | 검증 수단 |
| --- | --- | --- |
| `data-curator` | 관계 엣지 큐레이션, 근거 수집·필터 | `npm run audit:data` |
| `pipeline-engineer` | 수집·누적·파티션, 워크플로 | `npm test` + 라운드트립 확인 |
| `frontend` | 그래프·패널·레이아웃 | `npm run e2e` + 빌드 |
| `data-auditor` (QA) | 링크 생존·날짜·라벨·커버리지 교차 검증 | 감사 스크립트 종료 코드 |
| `release-writer` | README·ADR·공유 글 | 수치 대조 (문서 vs 실제 데이터) |

**QA 에이전트 주의점 (하네스 스킬 가이드 기준):**
- `Explore` 가 아니라 `general-purpose` 를 쓴다 — 읽기 전용이면 감사 스크립트를
  실행할 수 없다
- "파일이 있는가" 가 아니라 **경계면 교차 비교**를 시킨다. 이번 세션의 사고 중
  다수가 경계면이었다: 워크플로가 커밋하는 경로 vs 파이프라인이 쓰는 경로,
  문서에 적힌 수치 vs 실제 데이터, 근거 JSON vs 런타임에 합쳐지는 뉴스 신호
- 전체 완성 후 1회가 아니라 **모듈 완성 직후 점진적으로** 실행한다

## 권장 순서

1. ~~`npm run audit:data` — 감사를 결정적 명령으로~~ **완료**
2. 도메인 경계 lint — 하네스가 돌수록 경계가 녹는 것을 막는다
3. CLAUDE.md — 암묵 규칙 기록
4. `--dry` 관례 통일
5. 그다음 하네스 구축 (에이전트 정의 → 스킬 → 오케스트레이터)

1~4 를 건너뛰고 5 로 가면, 에이전트가 검증 없이 "완료" 를 보고하는 하네스가 된다.
지금 상태보다 나쁘다.
