# ADR 0003 — 하네스 엔지니어링을 위해 아직 없는 것

- 상태: 완료 (2026-08-29 구축)
- 날짜: 2026-08-29

## 왜 지금 이 문서인가

이 저장소의 작업은 지금까지 전부 단일 작업자가 즉흥적으로 처리했다. 같은 종류의
일이 반복되는데도 매번 처음부터 다시 판단했고, 그 과정에서 반복적으로 같은 유형의
사고가 났다. 하네스(전문 에이전트 + 스킬)를 붙일 만한 지점이 분명히 있다.

다만 **하네스를 지금 바로 구축하면 안 되는 이유**가 있어서, 무엇이 먼저인지를
먼저 기록한다. 하네스는 에이전트가 스스로 검증할 수단이 있을 때만 작동한다.
그 수단이 없으면 에이전트가 자기 결과를 확인 없이 보고하고, 그건 지금보다 나쁘다.

## 현황 감사

```
.claude/agents/    없음
.claude/skills/    없음
.claude/commands/  없음
CLAUDE.md          없음
```

즉 신규 구축 대상이다.

### 하네스가 이미 기댈 수 있는 것

에이전트가 스스로 "됐다/안 됐다"를 판정할 수단은 이번에 갖춰졌다.

| 수단 | 실행 | 소요 |
| --- | --- | --- |
| 단위 테스트 (도메인) | `npm test` | 약 0.4초 |
| E2E (실브라우저) | `npm run e2e` | 약 90초 |
| 타입 검사 | `npx tsc --noEmit` | 수초 |
| 빌드 | `npm run build` | 약 6초 |
| CI | push·PR 마다 위 셋 | — |

순수 도메인 층(ADR 0001)이 분리돼 있어 에이전트에게 좁고 검증 가능한 과제를
줄 수 있다. 파이프라인 스크립트는 대부분 `--dry` 를 지원해 파괴적 변경 전에
미리보기가 가능하다.

### 하네스가 붙을 반복 작업 (이번 세션에서 실제로 반복된 것)

| 작업 | 반복 횟수 | 현재 상태 |
| --- | --- | --- |
| 근거 수집·필터·재수집·검증 | 6회 (collect → filter → recollect → gdelt → rebuild → normalize) | 스크립트 6개, 조율 문서 없음 |
| 데이터 감사 (링크 생존·날짜·라벨·화이트리스트) | 4회 | 매번 임시 스크립트 작성 후 삭제 |
| Reddit 공유 글 작성 | 3회 (서브레딧별 프레이밍 상이) | 스크래치패드에만 존재 |
| 야간 파이프라인 사고 대응 | 3회 (누적 소실·git add 경로·수집시각) | 사후 대응 |

## 하네스 구축 전에 반드시 필요한 것

### 1. 데이터 감사를 실행 가능한 명령으로 — **완료 (2026-08-29)**

이번에 네 번 돌린 감사가 전부 임시 스크립트였고 매번 지워졌다. 확인한 항목:

- 화이트리스트 밖 매체 유입 (실제로 9건 발견)
- 링크 생존 — 404/410 (실제로 5건 발견)
- 날짜 정합성 — 미래 날짜, 수집창 위반, 형식 오류
- 매체명·제목 표기 품질 (실제로 443건 발견)
- 근거 커버리지 (218/266 → 64/266 변화 추적)

**에이전트에게 "데이터 품질을 확인하라" 고 지시하려면 판정이 결정적이어야 한다.**
`npm run audit:data` 가 종료 코드로 답하지 않으면, 에이전트는 "확인했습니다" 라고
보고하고 실제로는 아무것도 확인하지 않는다. 이것이 하네스 이전에 와야 하는 첫 번째다.

**구현됨.** `scripts/audit/` — 판정 규칙(`checks.mts`)과 I/O(`data.mts`)를 분리했고,
규칙에는 단위 테스트 29개가 붙어 있다. 감사 자체가 틀리면 감사가 무의미하므로
규칙도 검증 대상이다.

검사 항목은 전부 실제로 데이터에 들어왔던 문제다: 허용 목록 밖 매체 · 미래/형식오류
날짜 · GDELT 하한 위반 · 수집 시각 역전 및 정체 · 매니페스트와 파티션 불일치 ·
인물 id 참조 무결성 · HTML 엔티티 잔존 · 제목 내 매체명 중복 · 확인 불가 리다이렉트
URL · 엣지 내 중복 · **문서 수치와 실제 데이터의 괴리**.

불량 데이터를 주입해 종료 코드 1 을 반환하는 것까지 확인했다. CI 와 야간 워크플로
양쪽에 걸었고, 야간 쪽은 **커밋 전에** 돌린다 — 커밋된 뒤에 알면 되돌려야 한다.
WARN 은 CI 를 막지 않는다. 경고로 빌드를 세우면 아무도 경고를 안 본다.

### 2. 도메인 경계의 기계적 강제 — **완료 (2026-08-29)**

ADR 0001 이 "도메인은 `../data` 나 `node:fs` 를 import 하지 않는다" 고 규정하지만
**강제하는 것이 없었다.** 사람은 리뷰로 잡을 수 있지만 규칙을 문서에서만 읽는 쪽은
어긴다. 경계가 한 번 녹으면 ADR 0001 이 무효가 되고 단위 테스트가 다시 느려진다.

**구현됨.** `npm run audit:boundary` — 값 import 는 금지하고 타입 import 는
허용 경로(`../types`, 도메인 내부)에서만 받는다. 타입은 컴파일 후 사라지므로
런타임 결합이 없다. 판정 규칙(`boundary-rules.mts`)에 단위 테스트 15개.

ESLint 를 들이지 않았다. 이 저장소에 ESLint 설정이 없고, 규칙 하나를 위해
eslint + typescript-eslint + 설정을 얹는 것보다 이 검사가 가볍고 빠르다.
필요가 늘면 그때 옮긴다.

부수 정리: `HistoryArc` 를 `data/signal-history.ts` 에서 `types.ts` 로 옮겼다.
도메인이 타입이라도 데이터 층을 참조하면 그 층의 형태에 기대게 된다. 이제 규칙이
"도메인은 `../types` 만 본다" 로 단순해졌다.

위반을 주입해(`RELATIONSHIPS` 값 import + `node:fs`) 종료 코드 1 을 반환하는 것까지
확인했다. CI 에 걸었다.

### 3. CLAUDE.md — 암묵 규칙의 기록 — **완료 (2026-08-29)**

이번 세션에서 사고를 낸 규칙들은 전부 코드 어디에도 적혀 있지 않았다.

- 이 저장소 파일은 CRLF 다. `\n` 기준으로 치환하면 매칭이 조용히 실패한다
  (실제로 3회 발생)
- 파괴적 스크립트는 `--dry` 를 먼저 돌리고 제거율을 보고 반영한다
- LLM 배치는 판정을 못 받으면 원본을 유지한다 — 침묵을 삭제로 해석하면
  API 오류 한 번에 데이터가 날아간다 (dry-run 에서 503 2회 발생)
- `generatedAt` 은 재처리가 갱신하면 안 된다
- 워크플로가 커밋하는 경로는 출력 구조를 바꿀 때 함께 고쳐야 한다
  (실제로 야간 실행이 깨질 뻔했다)

에이전트는 새 세션마다 이걸 모른 채 시작한다. CLAUDE.md 가 없으면 같은 사고가
반복된다.

**구현됨.** `CLAUDE.md` 96줄. 매 세션 로딩되므로 짧게 유지하고 이유는 ADR 로 넘긴다.
담은 것은 "모르고 하면 사고가 나는 것" 만이다.

당초 "이 저장소는 CRLF" 로 알고 있었으나 실측하니 **CRLF 16 · LF 51 혼재**였다.
파일마다 다르니 가정할 수 없고, 그래서 치환 실패가 예측 불가했던 것이다.

가장 값이 큰 항목은 **"통과는 아무것도 증명하지 않는다"** 다. 이 저장소에서
"확인했다" 가 거짓이었던 사례가 반복됐다 — 링크 생존 20/20(실제로는 google 페이지가
200 을 준 것), 감사 통과인데 종료코드 127, E2E 간헐 실패. 검사를 만들면 실패도
시켜 본다는 규칙을 명시했다.

문서에 적은 명령·경로·ADR 참조가 실제와 맞는지 확인했다.

### 4. `--dry` 관례의 통일 — **완료 (2026-08-29)**

조사해 보니 문제는 이름이 아니라 **미리보기 수단 자체가 없는 것**이었다.
쓰기 스크립트 8개 중 7개는 이미 `--dry` 를 쓰고 있었고, `collect.mts` 만
`--fetch`(네트워크 단계 축)를 가진 채 **조건 없이 덮어쓰고 있었다**.

**구현됨.** `collect.mts` 에 `--dry` 를 추가하고, `npm run audit:conventions` 로
관례를 강제한다. 규칙은 `convention-rules.mts` (순수, 단위 테스트 16개).

규칙을 만드는 과정 자체가 교훈이었다. 첫 판정은 4건을 위반으로 잡았는데 전부
오탐이었다 — 캐시 쓰기(gitignore 대상)를 데이터 쓰기로 셌고, `dry` 를 함수 인자로
받거나 넘겨주는 형태를 가드로 인정하지 않았다. **통과시키려고 규칙을 완화하지 않고**
사실 판정을 정교화했다. 정교화 후에도 새 위반 파일을 넣으면 여전히 잡히는지
확인했다(종료 코드 1).

가드로 인정하는 세 형태:
  상수 분기  `if (DRY) {...} else { write }`      collect.mts
  인자 정의  `writeOutput(file, dry: boolean)`    merge.mts
  인자 전달  `writeOutput(file, dry, ...)`        pipeline.mts · finalize.mts

플래그는 등록제로 바꿨다. `--dry`(쓰지 않음) · `--fetch`(네트워크 축) ·
`--links`(느린 검사) 외의 플래그가 새로 생기면 실패한다. 방향이 섞이는 것을
사람 기억에 맡기지 않는다.

## 구축 결과 (2026-08-29)

선행 조건 1~4 를 끝낸 뒤 구축했다. 이번 세션의 실제 작업 분포에 근거한다.

| 에이전트 | 담당 | 검증 수단 |
| --- | --- | --- |
| `data-curator` | 관계 엣지 큐레이션, 근거 수집·필터 | `npm run audit:data` |
| `pipeline-engineer` | 수집·누적·파티션, 워크플로 | `npm test` + 라운드트립 확인 |
| `frontend` | 그래프·패널·레이아웃 | `npm run e2e` + 빌드 |
| `data-auditor` (QA) | 링크 생존·날짜·라벨·커버리지 교차 검증 | 감사 스크립트 종료 코드 |
| `release-writer` | README·ADR·공유 글 | 수치 대조 (문서 vs 실제 데이터) |

**QA 에이전트 주의점 (하네스 스킬 가이드 기준):**
- `Explore` 가 아니라 `general-purpose` 를 쓴다 — 읽기 전용이면 감사 스크립트를
  실행할 수 없다
- "파일이 있는가" 가 아니라 **경계면 교차 비교**를 시킨다. 이번 세션의 사고 중
  다수가 경계면이었다: 워크플로가 커밋하는 경로 vs 파이프라인이 쓰는 경로,
  문서에 적힌 수치 vs 실제 데이터, 근거 JSON vs 런타임에 합쳐지는 뉴스 신호
- 전체 완성 후 1회가 아니라 **모듈 완성 직후 점진적으로** 실행한다

## 실제로 만든 것

```
.claude/agents/   data-curator · pipeline-engineer · frontend · qa-auditor · release-writer
.claude/skills/   evidence-pipeline · data-integrity · polaris(오케스트레이터)
```

에이전트 정의에는 역할뿐 아니라 **이 저장소에서 실제로 났던 사고**를 원칙으로
적었다. "덮어쓰지 않고 누적한다", "generatedAt 은 재처리가 갱신하면 안 된다" 같은
것들은 전부 사고 후에 얻은 규칙이다. 새 세션이 그 사고를 다시 내지 않게 하는 것이
하네스의 실질적 값이다.

`qa-auditor` 는 `general-purpose` 성격으로 두었다 — 읽기 전용이면 감사 스크립트를
실행할 수 없다. 역할은 "파일이 있는가" 가 아니라 **경계면 교차 비교**다.
이 저장소 사고의 다수가 경계면이었다(워크플로 경로 vs 스크립트 출력 경로,
문서 수치 vs 실제 데이터, JSON 정리 vs 런타임 병합).

오케스트레이터(`polaris`)의 Phase 0 은 **한 영역이면 그 에이전트만 부르도록**
한다. 팀을 꾸리는 비용이 이득보다 큰 경우가 많고, 이 저장소의 변경은 대개
의존이 있어 병렬이 잘 맞지 않는다.

검증: 구조(frontmatter·commands 미생성)와 참조 무결성(에이전트·스킬·명령·ADR)을
확인했다. 모든 참조가 실재한다.
