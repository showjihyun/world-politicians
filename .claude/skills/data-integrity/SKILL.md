# 검증

이 저장소에서 **"확인했다" 가 거짓이었던 사례가 반복됐다.** 그래서 무엇을 어떻게
확인해야 통과라고 말할 수 있는지를 규칙으로 둔다.

## 통과는 아무것도 증명하지 않는다

실제로 있었던 거짓 통과:

| 무엇 | 왜 거짓이었나 |
| --- | --- |
| 링크 생존 20/20 | `news.google.com` 이 자기 페이지에 200 을 줬다. 기사 존재와 무관 |
| 감사 통과인데 종료 코드 127 | `process.exit()` 이 Windows 에서 이벤트 루프를 끊어 코드를 뭉갰다 |
| E2E "잘 돈다" | 고정 대기가 framer-motion 퇴장과 레이스여서 간헐 실패였다 |
| 관례 검사 위반 4건 | 전부 오탐. 캐시 쓰기를 데이터 쓰기로 셌다 |

**검사를 만들거나 믿기 전에 실패도 시켜 본다.** 불량을 주입해 종료 코드 1 이
나오는지 확인하지 않은 검사는 검사가 아니다.

## 명령

```
npm test               도메인·코어 단위 테스트 (약 0.5초)
npm run audit          경계 + 관례 + 데이터 감사 (종료 코드로 판정)
npm run audit:data -- --links   근거 링크 생존까지 (느림)
npm run e2e            실브라우저 53개 (약 90초)
npm run build          타입 + 번들
```

**종료 코드를 직접 확인한다.** 파이프를 통과시키면 `$?` 가 마지막 명령의 코드가
되어 판정이 뒤집힌다(실제로 겪었다). `cmd >/dev/null 2>&1; echo $?` 로 본다.

## 무엇을 건드렸으면 무엇을 돌리는가

| 변경 | 최소 검증 |
| --- | --- |
| 도메인 로직 | `npm test` |
| 데이터(엣지·근거) | `npm run audit:data` + README 수치 |
| 파이프라인 | `npm test` + 라운드트립 (아래) |
| 워크플로 | 명령을 로컬에서 그대로 재현 |
| 화면 | `npm run e2e` + **스크린샷 실제로 보기** |
| 무엇이든 | `npm run audit` |

## 파이프라인 라운드트립

쓰기 경로는 단위 테스트로 안 잡힌다. 이렇게 확인한다:

1. 기존 아카이브 읽기 → 건수 기록
2. **신규 0건**으로 병합 → 건수가 유지돼야 한다 (과거에 239 → 4 로 잘린 적 있다)
3. 쓰기
4. 다시 읽기 → 건수 동일, `generatedAt` 보존 확인

## 명령이 답하지 못하는 경계

이 저장소 사고의 다수는 단일 모듈이 아니라 경계면이었다. 직접 읽어 대조한다:

- **워크플로가 커밋하는 경로 vs 스크립트가 쓰는 경로** — 어긋나면 `git add` 가
  실패해 그날 데이터가 유실된다
- **문서의 수치 vs 실제 데이터** — `audit:data` 가 일부 대조하지만 새 수치는
  패턴을 추가해야 잡힌다
- **매니페스트 vs 파티션 실제 내용** — 화면의 "N건" 이 틀리게 된다
- **JSON 정리 vs 런타임 병합** — JSON 을 깨끗이 해도 런타임에 다른 소스가
  섞이면 화면에서는 그대로다

## 보고 방식

- 실행한 명령과 **종료 코드**를 적는다
- 검증하지 못한 범위는 "확인하지 못했다" 고 명시한다. 침묵은 통과로 읽힌다
- 실패를 발견하면 원인을 특정하되 직접 고치지 않고 담당에게 넘긴다
