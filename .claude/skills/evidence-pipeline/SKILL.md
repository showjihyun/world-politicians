# 근거 파이프라인

관계 엣지에 "어떻게 아느냐" 에 답할 링크를 붙이는 작업. 스크립트가 6개 있고
순서와 전제가 있어서, 모르고 돌리면 데이터를 망가뜨린다.

## 먼저 알아야 할 것

**근거는 확인 가능해야 한다.** Google News 리다이렉트(`news.google.com/rss/articles/...`)는
서버에서 따라가면 Google 페이지에서 멈추고, base64 안에 원본 주소가 없다.
목적지도 매체도 확인할 수 없으므로 **근거가 아니다.** `audit:data` 가 막는다.

**커버리지보다 검증 가능성이 우선이다.** 한때 218엣지/478링크였지만 94% 가
확인 불가 URL 이었다. 전면 재수집으로 64엣지/162링크가 됐고, 그쪽이 방어 가능하다.

**동반 언급은 근거가 아니다.** 두 이름이 같은 기사에 나오는 것과 그 관계를
뒷받침하는 것은 다르다. 관련성 필터가 후보의 절반 이상을 버리는 것이 정상이다.

## 스크립트

| 스크립트 | 하는 일 | 비고 |
| --- | --- | --- |
| `rebuild.mts` | GDELT 로 전면 재수집 + 관련성 필터 + 링크 생존 확인 | 기본 경로. 원본 URL 만 남는다 |
| `gdelt.mts` | 근거 없는 엣지만 아카이브에서 보강 | 2017년 이후만 |
| `collect.mts` | Google News 로 후보 수집 | 확인 불가 URL 이 나오므로 지금은 쓰지 않는다 |
| `recollect.mts` | 사건 키워드로 재검색 | |
| `filter.mts` | LLM 관련성 필터 | |
| `normalize.mts` | 제목·매체명 표기 정리 | |

전부 `--dry` 를 지원한다. `--dry` 는 "쓰지 않는다" 이며, 이 방향은 저장소 전체
공통이다(`npm run audit:conventions` 가 강제).

## 절차

1. **현재 상태를 본다** — `npm run audit:data` 로 커버리지와 문제를 확인한다
2. **`--dry` 로 먼저 돌린다** — 제거율과 샘플을 본다. 필터가 802 → 381(52% 제거)
   이었던 적이 있고, 이 수치를 보지 않고 반영했으면 되돌리기 어려웠다
3. **수치를 판단한다** — 제거율이 10% 미만이면 필터가 일을 안 한 것이고,
   80% 이상이면 근거 없는 엣지가 대량 발생해 오히려 후퇴다
4. **반영하고 감사한다** — `npm run audit:data` 종료 코드가 0 이어야 한다
5. **문서를 고친다** — 커버리지가 바뀌었으면 README 수치도. 감사가 대조한다

## GDELT 를 쓸 때

**검색어보다 시기가 중요하다.** 2017~현재 전 구간을 검색하면 구절 조건이 사실상
무시되고 최근 일반 기사만 돌아온다(`bush×cheney` 질의에 "How socialists took over
the Democratic Party" 가 나온 적이 있다). 사건이 일어난 달로 창을 좁히면 정확해진다.

```
"biden mccain eulogy"  2018-08~10  → Joe Biden heartfelt eulogy for John McCain (WaPo)
```

그 외 제약:
- HTTPS 핸드셰이크가 실패해 HTTP 로 호출한다(공개 메타데이터, 자격증명 없음)
- 커버리지 하한 201701. 그 이전은 `Invalid query start date`
- 쿼리에 `(domain:a OR domain:b)` 를 넣으면 구절 조건이 깨진다 → 클라이언트에서 필터
- 같은 기사를 모바일·지역판 URL 로 중복 반환 → 제목 정규화로 중복 제거

## LLM 배치를 쓸 때

**판정을 못 받은 항목은 원본을 유지한다.** 침묵을 삭제로 해석하면 API 오류
한 번에 그 배치의 근거가 통째로 날아간다. 실제로 dry-run 중 503 이 2회 났다.

관련성 판정 프롬프트에는 **그 엣지의 주장(note)을 함께 넣는다.** "이 기사가 두
사람과 관련 있나" 가 아니라 "이 기사가 *이 주장*의 근거인가" 를 물어야 한다.
